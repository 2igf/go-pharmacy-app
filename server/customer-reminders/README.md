# Personal manual reminders

`manualReminders` stores customer-entered reminder definitions separately from the disabled legacy `medicationReminders` and `medicationReminderLogs` clinical domain. It does not prescribe medication, infer doses, establish patient relationships or enable clinical operations.

- All procedures require an authenticated account whose **persisted** platform role is `user`. Ownership comes from the authenticated server context. Inputs are strict and reject owner, role and clinical fields.
- `list`, `detail`, `create`, `update`, `remove`, `history` and `record` operate only on that account. Unknown and foreign identifiers both return the same `NOT_FOUND` response. Returned definitions include `userId` for native account cleanup; create request hashes and request IDs remain private server metadata.
- A definition contains the name and optional dosage/notes typed by the user, up to eight distinct daily times, selected weekdays (`0` is Sunday), inclusive start/end local dates, and an IANA timezone. Times and weekdays are normalized into sorted arrays. Notifications default to discreet generic content.
- There may be at most 20 enabled definitions and 100 definitions in total per account. A user-row transaction lock serializes capacity checks, create retries, edits and reports for that owner.
- Create requests carry a UUID `requestId`, unique for that account. Identical retries return the current stored definition. Reusing the ID with a different original normalized payload returns `CONFLICT`. Deleting a definition also deletes its retry key; clients must generate a new UUID for each deliberate new definition.
- Updates replace the editable fields and require the current version; pause/resume is an update to `enabled`. Every accepted edit increments `version`. Delete also requires the current version and cascades **only that definition's new manual event rows**. History deletion is therefore permanent when the user confirms deletion in the UI.
- History is immutable and bounded to the latest 50 events by default (maximum 100). `taken` and `skipped` mean **user reported** only. Notification delivery, opening a page and automatic scheduling never create these records. Retrying the same occurrence/status/zone returns the stored event; a conflicting report returns `CONFLICT`.
- A report must match an entered scheduled minute/day/date, be no later than server time, no more than seven days old, and no earlier than the minute the definition was created. A paused definition cannot acquire a new report. Definition version is required to reject stale clients.
- The saved definition timezone is provenance. Native notifications follow the device timezone. A report may explicitly supply the device IANA timezone; the server validates the occurrence in that zone and stores it with the event as **user-reported timezone provenance**, without rewriting the definition or treating it as clinical evidence. If omitted, the saved zone is used.
- Schedule changes do not rewrite existing history. This API is not a delivery ledger, medical adherence score, prescription schedule or audit of whether medication was actually consumed. Data is private in transport/authentication, but database encryption at rest remains an infrastructure concern.

No reminder names, dose text or notes are logged by this module. Native notification permission, inexact delivery, boot recovery and encrypted local scheduling are separate platform concerns.

The focused suite is `server/customer-reminders.integration.test.ts`. Without `TEST_DATABASE_URL` it runs only schedule validation. Database cases require the coordinator's authorized disposable V2 database, migration 0007 and fixture cleanup for `customerReminderEvents` before `customerReminders` before `users`.
